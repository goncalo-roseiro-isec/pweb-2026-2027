0. Antes de começar

0.1 O que vamos construir

A ficha 3 arranca a aplicação Gestão de Loja, a primeira das três aplicações do trabalho prático. É uma Blazor Web App que serve de backoffice da loja: é nela que o administrador gere os produtos, as categorias e os modos de entrega. Fala diretamente com a base de dados, sem passar pela API.

A aplicação é feita em três fichas:

Ficha O que se faz Como fica a aplicação no fim
3 (esta) Projeto com autenticação, classes de domínio, contexto de base de dados, configuração e código de arranque Compila, mas ainda não tem base de dados nem páginas de gestão
4 Criação da base de dados FrutariaPWeb com migrations Arranca e cria sozinha os roles e o utilizador administrador
5 Páginas Home e Sobre, menu, e as páginas de gestão (CRUD) de categorias, produtos e modos de entrega Completa: faz-se login como administrador e gerem-se os dados

Atenção. A meio desta ficha (alínea 3.k) a aplicação deixa de arrancar, e só volta a arrancar quando a base de dados for criada, na ficha 4. Não é um erro. A partir desse ponto a ficha pede apenas para compilar.

0.2 Como ler este guia

Cada passo corresponde a uma alínea da ficha e tem sempre os mesmos blocos, pela mesma ordem:

  • Quadro do passo: a alínea da ficha, a ação (criar, alterar, apagar), o caminho exato do ficheiro ou da pasta, e como lá chegar no Visual Studio.
  • O que vamos fazer: o objetivo do passo, numa frase.
  • Código: o ficheiro completo, com um botão para copiar. Nos ficheiros que já existiam, as linhas novas ou alteradas aparecem destacadas.
  • Porquê: a razão de cada decisão.
  • Verificar: o que confirmar antes de avançar para o passo seguinte.

Os conceitos (Identity, Entity Framework Core, relações entre entidades, connection string, arranque da aplicação) estão explicados nos slides da ficha 3. Aqui fica só o que é preciso para executar cada passo.

2. Relações entre entidades (etapa 2 da ficha)

A etapa 2 da ficha é teórica: apresenta o vocabulário das relações no Entity Framework Core e quatro convenções para escrever uma relação de um para muitos (1-N). A explicação completa, com diagramas, está nos slides. Para executar a alínea 3.b basta reter o seguinte.

Numa relação 1-N, por exemplo "uma categoria tem muitos produtos":

  • a entidade principal é a do lado 1 (Categoria);
  • a entidade dependente é a do lado N (Produto), e é na tabela dela que fica a chave estrangeira;
  • uma propriedade de navegação é uma propriedade C# que aponta para a entidade relacionada: de referência quando aponta para um objeto (produto.categoria), de coleção quando aponta para muitos (modoEntrega.produtos).

As quatro convenções da ficha diferem no que se escreve nas classes:

Convenção Na entidade dependente Na entidade principal
1 navegação de referência nada
2 nada navegação de coleção
3 navegação de referência navegação de coleção
4 chave estrangeira e navegação de referência navegação de coleção

Nas classes que vamos escrever há duas relações:

Relação O que se escreve Efeito
Categoria (1) para Produto (N) Em Produto: int CategoriaId e Categoria categoria. Em Categoria: nada Obrigatória: todo o produto tem categoria
ModoEntrega (1) para Produto (N) Em Produto: int? ModoEntregaId e ModoEntrega modoentrega. Em ModoEntrega: ICollection<Produto>? produtos Opcional: o ? em int? permite produtos sem modo de entrega. É a convenção 4 completa

A ver, sem alterar: o bloco AuthorizeView

Com o NavMenu.razor ainda aberto, vale a pena olhar para o bloco que vem a seguir às entradas do menu. Simplificado, é isto:

<AuthorizeView>
    <Authorized>
        <!-- só aparece com sessão iniciada: o nome do utilizador e o botão Logout -->
    </Authorized>
    <NotAuthorized>
        <!-- só aparece sem sessão iniciada: as ligações Register e Login -->
    </NotAuthorized>
</AuthorizeView>

AuthorizeView é um componente do Blazor que mostra conteúdo diferente consoante quem está a ver a página:

Zona Quando aparece O que o template lá põe
<Authorized> Há um utilizador com sessão iniciada O nome do utilizador (@context.User.Identity?.Name) e o botão Logout
<NotAuthorized> Ninguém fez login As ligações Register e Login

É por isto que, depois do login, Register e Login desaparecem do menu e aparecem o nome do utilizador e o Logout. O componente sabe quem está a ver porque, depois do login, um cookie identifica o utilizador em cada pedido, e o Program.cs entrega esse estado a todos os componentes (linha AddCascadingAuthenticationState).

Atenção. Esconder uma ligação não protege a página. AuthorizeView só decide o que se mostra; quem souber o endereço chega lá na mesma. O que impede a entrada numa página é a linha @attribute [Authorize] no topo dela, como se vê em GestaoLoja/Components/Pages/Auth.razor (a entrada Auth Required do menu): sem sessão iniciada, quem lá for é enviado para o login.

Nota. AuthorizeView também aceita roles: <AuthorizeView Roles="Admin"> mostra o conteúdo só a administradores. O menu da loja, na ficha 5, usa este componente para mostrar as opções de gestão apenas a quem tem sessão iniciada.

    public string? Nome { get; set; }

    public string? Apelido { get; set; }

    public string? Telemovel { get; set; }

    // Validado pelo atributo validarNIF, definido no fim deste ficheiro.
    [validarNIF(ErrorMessage = "O NIF é inválido.")]
    public long? NIF { get; set; }

    // Fotografia do utilizador, guardada na base de dados como bytes.
    public byte[]? Fotografia { get; set; }

    // Estado da conta. Um utilizador novo começa como Pendente.
    public string Estado { get; set; } = EstadoUtilizador.Pendente;

    // Data de registo, preenchida quando o objeto é criado (hora UTC).
    public DateTime DataRegisto { get; set; } = DateTime.UtcNow;
}

// Um atributo de validação escrito por nós, para usar como [validarNIF].
// Herda de ValidationAttribute, a classe base de atributos como [Required]
// e [StringLength]. Basta reescrever o método IsValid: recebe o valor do campo
// e devolve sucesso ou uma mensagem de erro, que o formulário mostra.
public class validarNIF : ValidationAttribute
{
    protected override ValidationResult? IsValid(object? value, ValidationContext validationContext)
    {
        if (value == null)
        {
            return new ValidationResult("O NIF é obrigatório.");
        }

        if (value is not long nif || nif.ToString().Length != 9)
        {
            return new ValidationResult("O NIF deve conter exatamente 9 dígitos.");
        }

        // Verificar se o NIF é válido (usando cálculo do dígito de controlo)
        if (!IsValidNIF(nif))
        {
            return new ValidationResult("O NIF é inválido.");
        }

        // Caso seja válido, retorna sucesso
        return ValidationResult.Success;
    }

    // O algoritmo de validação do NIF usado pelas Finanças (módulo 11).
    // O nono dígito é um dígito de controlo, calculado a partir dos oito primeiros:
    // se o cálculo não der o nono dígito, o número não é um NIF válido.
    private bool IsValidNIF(long nif)
    {
        string nifString = nif.ToString();

        // Primeiro dígito do NIF entre 1 e 9
        int primeiroDigito = int.Parse(nifString[0].ToString());
        if (primeiroDigito < 1 || primeiroDigito > 9)
        {
            return false;
        }

        // Calcular o dígito de controlo:
        // somar os oito primeiros dígitos multiplicados por 9, 8, 7, 6, 5, 4, 3 e 2
        int total = 0;

        for (int i = 0; i < 8; i++)
        {
            total += int.Parse(nifString[i].ToString()) * (9 - i);
        }

        // O dígito de controlo é 11 menos o resto da divisão da soma por 11.
        // Se der 10 ou 11, o dígito de controlo é 0.
        int digitoDeControlo = 11 - (total % 11);
        if (digitoDeControlo >= 10)
        {
            digitoDeControlo = 0;
        }

        // O NIF é válido se o dígito calculado for igual ao nono dígito.
        return digitoDeControlo == int.Parse(nifString[8].ToString());
    }
}

using Microsoft.AspNetCore.Identity;

namespace GestaoLoja.Data;

// Cria os dados sem os quais a aplicação não se consegue usar:
// os três roles e um utilizador administrador.
// A classe é static: não guarda dados nem se criam objetos dela. Serve só para
// arrumar o método abaixo, que o Program.cs chama em cada arranque da aplicação.
public static class Inicializacao
{
    // Recebe os dois serviços do Identity que gerem utilizadores e roles.
    // Não os cria: é o Program.cs, que chama este método, que os entrega.
    // É async porque cada operação vai à base de dados; o await liberta a thread
    // enquanto se espera pela resposta.
    public static async Task CriaDadosIniciais(UserManager<ApplicationUser> userManager,
        RoleManager<IdentityRole> roleManager)
    {
        // Os roles por omissão: os três perfis de utilizador da aplicação.
        string[] roles = ["Admin", "Gestor", "Cliente"];

        foreach (var role in roles)
        {
            // Só cria o role se ainda não existir. Este método corre em todos
            // os arranques e não pode criar os mesmos dados duas vezes.
            if (!await roleManager.RoleExistsAsync(role))
            {
                IdentityRole roleRole = new IdentityRole(role);
                await roleManager.CreateAsync(roleRole);
            }
        }

        // O utilizador por omissão: o administrador.
        // Aqui é só um objeto em memória; ainda nada foi gravado.
        var defaultUser = new ApplicationUser
        {
            UserName = "admin@localhost.com",
            Email = "admin@localhost.com",
            Nome = "Administrador",
            Apelido = "Local",
            // O Program.cs exige conta confirmada para fazer login
            // (RequireConfirmedAccount = true). Sem isto, o administrador não entrava.
            EmailConfirmed = true,
            PhoneNumberConfirmed = true
        };
        // Confirma que nenhum utilizador já gravado tem o Id deste objeto novo.
        if (userManager.Users.All(u => u.Id != defaultUser.Id))
        {
            // Só cria o administrador se ainda não houver ninguém com este email.
            var user = await userManager.FindByEmailAsync(defaultUser.Email);
            if (user == null)
            {
                // Grava o utilizador. A palavra-passe não é guardada: guarda-se o seu hash.
                await userManager.CreateAsync(defaultUser, "Is3C..00");
                // Dá-lhe o role Admin: uma linha na tabela AspNetUserRoles.
                await userManager.AddToRoleAsync(defaultUser, "Admin");
            }
        }
    }
}

Porquê. O sítio do bloco não é arbitrário. Antes de builder.Build() os serviços estão apenas registados, ainda não existem. Depois de Build() já existem e podem ser pedidos. E tem de ficar antes de app.Run(), que é a linha em que a aplicação começa a atender pedidos e da qual o código só sai quando a aplicação termina.

Linha O que faz
app.Services.CreateScope() O UserManager e o RoleManager são serviços com tempo de vida Scoped: normalmente vivem durante um pedido HTTP. No arranque não há pedido nenhum, por isso cria-se um scope à mão
using (...) { } No fim do bloco, o scope e os serviços criados dentro dele são libertados
GetRequiredService<...>() Pede o serviço ao contentor de injeção de dependências. Lança uma exceção se o serviço não estiver registado (é o que acontece se faltar o AddRoles da alínea 3.i)
await Inicializacao.CriaDadosIniciais(...) Cria os roles e o administrador, se ainda não existirem
try e catch com throw Tal como está, o erro segue em frente sem alteração. É o sítio onde mais tarde se pode registar o erro num log
