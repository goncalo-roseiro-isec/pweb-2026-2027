0. Antes de começar

0.1 O que vamos fazer

A ficha 7 começa a terceira aplicação do semestre: a FrutiLândia, a loja que os clientes usam. É o frontend: corre como página web e como app instalada (Windows, Android, iOS), a partir de um único código. Não tem base de dados própria: pede tudo à RESTfulAPI da ficha 6.

FichaAplicaçãoPara quem
2App Utilidades (MAUI + Web + RCL)treino: a mesma estrutura, com dados inventados
3 a 5Gestão de Loja (Blazor)o Admin e o Gestor: o backoffice
6RESTfulAPIas apps: a porta de entrada para os dados
7 (esta)FrutiLândia (MAUI + Web + 4 RCL)os clientes: hoje só a estrutura; as páginas a sério vêm nas próximas fichas

Nesta ficha não há conceitos novos. É a estrutura da ficha 2 outra vez, com duas diferenças: há quatro bibliotecas em vez de uma, e os dados vêm da API em vez de serem inventados. Os passos, pela ordem da ficha:

  1. Etapa 1: criar a app nativa ProdutosMAUI (Blazor Hybrid).
  2. Etapa 2: acrescentar a app web ProdutosBlazor (Aplicativo Web Blazor).
  3. Etapa 3: acrescentar quatro Razor Class Library: RCLAPI, RCLComum, RCLProdutos e RCLCompras.
  4. Configuração: as dependências entre projetos, o pacote NuGet, os _Imports, os Routes, o AppConfig, o Program.cs, o MauiProgram.cs e a pasta images.

Slides e guia. Os slides da ficha 7 mostram onde esta aplicação encaixa na arquitetura. Este guia é a resolução: em cada passo, o ficheiro, onde fica, e o código completo para copiar.

0.2 Onde entra a FrutiLândia

Há duas aplicações para pessoas e uma base de dados. A Gestão de Loja fala diretamente com a base de dados; a FrutiLândia nunca: passa sempre pela API.

Uma forma simples de ver: a Gestão de Loja é o armazém, onde o gestor arruma a mercadoria; a API é o balcão; a FrutiLândia é a montra que o cliente leva no bolso. A montra não vai ao armazém: pede ao balcão.

0.3 A solução por dentro

A solução Frutilandia tem seis projetos, arrumados em quatro andares. Cada projeto só conhece os que estão por baixo.

ProjetoTemplateO que vai terNa ficha 2 era...
ProdutosMAUIAplicativo .NET MAUI Blazor Hybrido arranque nativo, a página anfitriã (index.html), o layout, a HomeMauiUtilidades
ProdutosBlazorAplicativo Web Blazoro servidor web, a página anfitriã (App.razor), o layout, a HomeBlazorUtilidades
RCLAPIBiblioteca de Classes Razortudo o que fala com a API: hoje o AppConfig e um teste de ligação; depois os DTOs e os serviçosa pasta Data da UtilidadesRCL
RCLComumBiblioteca de Classes Razoro que todos partilham: o menu, o Bootstrap, o app.css, o ícone; depois os componentes comunsas pastas wwwroot e Shared da UtilidadesRCL
RCLProdutosBiblioteca de Classes Razoras páginas dos produtos (hoje, uma provisória)a pasta Pages da UtilidadesRCL
RCLComprasBiblioteca de Classes Razoras páginas das compras (hoje, uma provisória)idem

Porquê. Com uma só RCL, tudo ia parar à mesma gaveta: menus, serviços, páginas de produtos, carrinho. Com quatro, cada coisa tem o seu sítio, e as regras de dependência obrigam a manter a arrumação: uma página de produtos não consegue, por engano, mexer no carrinho, porque a RCLProdutos nem sabe que a RCLCompras existe.

Interatividade local: Global, e não Per page/component

As páginas da FrutiLândia vão estar nas RCL, e as RCL são usadas pelas duas apps. O MAUI é sempre interativo e dá erro quando um componente tem @rendermode:

NotSupportedException: Cannot supply a component of type ... because the current platform does not support the render mode ...

Com Global, o @rendermode fica num só sítio, o App.razor da Web, e os componentes não o têm. É a escolha da ficha 2.

Quem já criou com Per page/component não precisa de recomeçar: na secção 4.d, o App.razor completo já traz o @rendermode="InteractiveServer" no HeadOutlet e no Routes, e fica igual.

ProdutosMAUI/ProdutosMAUI.csproj e ProdutosBlazor/ProdutosBlazor.csproj (excerto)

<ItemGroup>
  <ProjectReference Include="..\RCLAPI\RCLAPI.csproj" />
  <ProjectReference Include="..\RCLComum\RCLComum.csproj" />
  <ProjectReference Include="..\RCLCompras\RCLCompras.csproj" />
  <ProjectReference Include="..\RCLProdutos\RCLProdutos.csproj" />

Porquê. As setas só descem. Quem está em baixo nunca conhece quem está em cima: a RCLAPI não sabe que há páginas, a RCLComum não sabe que há um carrinho. Se uma RCL de baixo referenciasse uma de cima, formava-se um círculo (A precisa de B, B precisa de A), e o Visual Studio recusa a referência. A RCLProdutos e a RCLCompras também não se conhecem: se um dia precisarem de partilhar alguma coisa, essa coisa desce para a RCLComum (se é visual) ou para a RCLAPI (se são dados).

Nota. As referências passam de uns para outros: o ProdutosMAUI já "vê" a RCLAPI através da RCLProdutos. Marcam-se as quatro na mesma, para o .csproj de cada app dizer, por escrito, de quem depende.

Atenção. A versão tem de ser 8.0.x, como o resto da solução. Sem -Version, o NuGet instala a mais recente, feita para um .NET mais novo, e arrasta outros pacotes Microsoft.Extensions.* para essa versão. Atenção também ao -ProjectName: sem ele, o pacote vai para o projeto escolhido na caixa "Projeto padrão" da consola.

Porquê. Um HttpClient é o objeto que faz os pedidos HTTP. Criar um novo em cada pedido gasta ligações e obriga a repetir a configuração (endereço, headers). A fábrica (IHttpClientFactory) guarda essa configuração uma vez e entrega clientes já prontos, reaproveitando as ligações. Na Web vem com o ASP.NET Core; no MAUI instala-se.

O que vamos fazer. Guardar num só sítio o endereço da API, para as duas apps o lerem.

RCLAPI/AppConfig.cs

namespace RCLAPI;

// A configuração da FrutiLândia, num só sítio.
// As duas apps (ProdutosMAUI e ProdutosBlazor) leem daqui.
public static class AppConfig
{
    // Onde está a RESTfulAPI (ficha 6)?
    //   false = localhost: só no PC (Web e Windows Machine). É o mais simples.
    //   true  = Dev Tunnel: funciona em todo o lado, também no emulador Android.
    public const bool UsarTunel = false;

    // localhost: a porta https do launchSettings.json da RESTfulAPI
    public const string ApiUrlLocal = "https://localhost:7123/";

    // Dev Tunnel: o URL do vosso túnel, SEM o /swagger e COM a / no fim
    public const string ApiUrlTunel = "https://abcd1234-7123.uks1.devtunnels.ms/";

    // O endereço que as apps usam (não mexer: muda com o UsarTunel)
    public static string ApiUrl => UsarTunel ? ApiUrlTunel : ApiUrlLocal;

    // Nome do HttpClient que fala com a API (Program.cs e MauiProgram.cs)
    public const string ApiClientName = "RESTfulAPI";

    // Header que salta a página de aviso do Dev Tunnel (ficha 6, secção 3.b);
    // em localhost não faz nada
    public const string DevTunnelHeader = "X-Tunnel-Skip-AntiPhishing-Page";
}

O endereço: localhost ou túnel

Para esta ficha pode ficar como está: o HttpClient só é usado no Extra (secção 7). Quem fizer o extra escolhe uma de duas maneiras:

UsarTunel = false (localhost)UsarTunel = true (Dev Tunnel)
O que pôrem ApiUrlLocal, a porta https da RESTfulAPI: está em Properties/launchSettings.json da API, na linha applicationUrl (no guia, 7123)em ApiUrlTunel, o endereço do túnel DevTunnelPWeb (ficha 6, secção 3.b), sem o swagger/index.html e com a / no fim
Funciona emWeb e MAUI em Windows MachineWeb, Windows Machine, emulador Android e telemóvel
Arrancar a APIF5 normal, perfil httpscom o túnel ativo

Por omissão está false: é o mais simples para testar no PC. Para o Android, muda-se só essa palavra para true; o resto do código não muda.

Porquê. Porquê o túnel para o Android? No emulador, localhost é o próprio telemóvel, não o PC; e o certificado HTTPS de desenvolvimento do PC não é aceite pelo Android. O túnel tem um endereço público e um certificado verdadeiro: funciona igual em todo o lado.

E ainda. Porquê const numa classe static? É configuração que não muda enquanto a app corre, e assim lê-se em qualquer lado sem criar objetos. O ApiUrl é a única exceção: é uma propriedade (=>) que devolve um dos dois endereços consoante o UsarTunel, e é ela que o Program.cs e o MauiProgram.cs usam. O header X-Tunnel-Skip-AntiPhishing-Page é o da ficha 6: com o túnel, sem ele, a resposta é a página de aviso em HTML em vez do JSON da API; em localhost é ignorado.

Etapa da ficha

Ação
Alterar ficheiro

O que vamos fazer. Registar o HttpClient da API e dizer ao servidor que também há páginas nas RCL.

ProdutosBlazor/Program.cs (ficheiro completo, com as linhas novas ou alteradas destacadas)

using ProdutosBlazor.Components;
using RCLAPI;

var builder = WebApplication.CreateBuilder(args);

// 1. Serviços: o que o contentor sabe criar
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();

// HttpClient para a RESTfulAPI: o endereço vem do AppConfig (RCLAPI)
builder.Services.AddHttpClient(AppConfig.ApiClientName, client =>
{
    client.BaseAddress = new Uri(AppConfig.ApiUrl);
    client.DefaultRequestHeaders.Add(AppConfig.DevTunnelHeader, "true");
});
builder.Services.AddScoped(sp => sp.GetRequiredService<IHttpClientFactory>()
    .CreateClient(AppConfig.ApiClientName));

var app = builder.Build();

// 2. Pipeline: por onde passa cada pedido HTTP
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Error", createScopeForErrors: true);
    app.UseHsts();
}

app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseAntiforgery();

app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode()
    .AddAdditionalAssemblies(
        typeof(RCLComum._Imports).Assembly,
        typeof(RCLProdutos._Imports).Assembly,
        typeof(RCLCompras._Imports).Assembly);

app.Run();
  • AddHttpClient(nome, configuração): regista na fábrica um cliente com nome, com o endereço da API e o header do túnel. A configuração escreve-se uma vez.
  • AddScoped(sp => ...CreateClient(nome)): quando um componente faz @inject HttpClient, o contentor pede à fábrica um cliente com esse nome. É assim que o EstadoApi recebe um HttpClient já configurado.
  • AddAdditionalAssemblies(...): o mesmo que o AdditionalAssemblies do Routes.razor, mas para o servidor. O Routes.razor trata da navegação com a app já aberta; o Program.cs trata do primeiro pedido (escrever o endereço ou recarregar). Sem esta linha, recarregar /produtos dá 404.

Os registos ficam antes do builder.Build(): depois dele, o contentor fica fechado.

A estrutura não volta a mudar: as próximas fichas enchem as gavetas. Os DTOs (copiados da API) e os serviços que usam o HttpClient vão para a RCLAPI; o catálogo e o detalhe dos produtos para a RCLProdutos; o carrinho e as compras para a RCLCompras; o que for preciso em mais do que um sítio para a RCLComum. O que vamos fazer. Um componente que pergunta à API pelas categorias e mostra só o status code.

RCLAPI/EstadoApi.razor

@inject HttpClient Http

<div class="alert @classe" role="status">
    <strong>RESTfulAPI:</strong> @mensagem
</div>

@code {
    private string mensagem = "a verificar a ligação...";
    private string classe = "alert-secondary";

    protected override async Task OnInitializedAsync()
    {
        try
        {
            // Pede a lista de categorias e só olha para o status code
            var resposta = await Http.GetAsync("api/categorias");

            mensagem = $"{(int)resposta.StatusCode} {resposta.StatusCode} em {Http.BaseAddress}api/categorias";
            classe = resposta.IsSuccessStatusCode ? "alert-success" : "alert-warning";
        }
        catch (Exception ex)
        {
            // Não chegou resposta nenhuma: sem internet ou endereço mal escrito
            mensagem = $"sem ligação a {Http.BaseAddress} ({ex.Message})";
            classe = "alert-danger";
        }
    }
}
  • @inject HttpClient Http: pede ao contentor o HttpClient registado no Program.cs e no MauiProgram.cs (4.i e 4.j), já com o endereço da API.
  • "api/categorias" é um caminho relativo: junta-se ao BaseAddress e dá https://...devtunnels.ms/api/categorias.
  • Verde (alert-success) com 200 OK: a API respondeu. Amarelo: chegou uma resposta, mas de erro (por exemplo, com a API parada é o túnel que responde, com um erro). Vermelho: não chegou resposta nenhuma (sem internet, ou endereço mal escrito).

Porquê. Fica na RCLAPI porque fala HTTP, e a regra é que só a RCLAPI conhece o HttpClient. As páginas a sério não vão usar o HttpClient: vão pedir os dados a serviços da RCLAPI, com interface e registo, como na ficha 2.
