0. Antes de começar

0.1 O que vamos fazer

A ficha 4 cria a base de dados FrutariaPWeb a partir das classes escritas na ficha 3. Não se escreve código: correm-se dois comandos no Visual Studio e confirma-se, tabela a tabela, que a base de dados ficou como as classes descrevem.

Ficha O que se faz Como fica a aplicação no fim
3 Projeto com autenticação, classes de domínio, contexto de base de dados, configuração e código de arranque Compila, mas não arranca: a base de dados ainda não existe
4 (esta) Criação da base de dados FrutariaPWeb com migrations, e verificação das tabelas Arranca outra vez e cria sozinha os roles e o utilizador administrador
5 Páginas Home e Sobre, menu, e as páginas de gestão (CRUD) de categorias, produtos e modos de entrega Completa: faz-se login como administrador e gerem-se os dados

São dois comandos, escritos no Console do Gerenciador de Pacotes:

Comando O que faz Mexe na base de dados?
Add-Migration BDInicial Compara as classes com a última migration e escreve, em C#, o que falta criar na base de dados Não. Só cria ficheiros no projeto
Update-Database Executa as migrations que ainda não foram aplicadas Sim. Cria a base de dados e as tabelas

Os conceitos (ORM, migrations, a tabela __EFMigrationsHistory, o que cada anotação faz à coluna) estão explicados nos slides da ficha 3 e nos slides desta ficha. Aqui fica o que é preciso para executar e verificar cada passo.

3.a Gerar a migration: Add-Migration BDInicial

Alínea da ficha
3.a
Ação
Executar
Onde
Console do Gerenciador de Pacotes, com GestaoLoja em "Projeto padrão". Os ficheiros são criados em GestaoLoja/Data/Migrations/ ou em GestaoLoja/Migrations/ (secção 0.6)
Como lá chegar
menu Ferramentas > Gerenciador de Pacotes do NuGet > Console do Gerenciador de Pacotes (Figura 1 da ficha). A consola abre na parte de baixo do Visual Studio; escrever o comando à frente de PM> e carregar em Enter

O que vamos fazer. Pedir ao Entity Framework que compare as classes com a última migration e escreva, num ficheiro C#, as instruções para pôr a base de dados igual às classes.

Add-Migration BDInicial

A consola mostra Build started... e Build succeeded., porque o comando começa por compilar o projeto. No fim aparece To undo this action, use Remove-Migration. e o Visual Studio abre o ficheiro da migration que acabou de criar.

Nota. Pode aparecer um aviso a começar por No store type was specified for the decimal property 'EmStock' on entity type 'Produto'. É o aviso anunciado na alínea 3.b da ficha 3: EmStock é decimal sem [Column], e o Entity Framework usa decimal(18,2). Não impede nada e pode ignorar-se.

Porquê. O Add-Migration faz quatro coisas, por esta ordem:

  1. compila o projeto (se houver erros, pára aqui com Build failed.);
  2. constrói o modelo a partir do ApplicationDbContext: os três DbSet, as classes da pasta Entities, o ApplicationUser e as tabelas que o IdentityDbContext traz;
  3. compara esse modelo com a fotografia guardada na última migration (o ficheiro ApplicationDbContextModelSnapshot.cs), ou com um modelo vazio, se ainda não houver migrations;
  4. escreve as diferenças como código C#, num ficheiro novo, e atualiza a fotografia.

Não toca na base de dados. Nesta altura a FrutariaPWeb continua a não existir.

O nome BDInicial é escolhido por nós: identifica a migration e deve dizer o que ela faz. O comando não distingue maiúsculas de minúsculas.

Ficheiro O que é Mexe-se nele?
<data>_BDInicial.cs A migration: o método Up aplica as alterações (cria tabelas, acrescenta colunas) e o método Down desfá-las Não
<data>_BDInicial.Designer.cs Informação interna do Entity Framework sobre esta migration Não
ApplicationDbContextModelSnapshot.cs A fotografia do modelo depois desta migration. É com ela que o próximo Add-Migration vai comparar Não

<data> é a data e a hora em que o comando correu, no formato AAAAMMDDhhmmss (por exemplo 20261028101532_BDInicial.cs). É o que mantém as migrations por ordem.

O Add-Migration corre o Program.cs só até à linha var app = builder.Build();, para saber como o contexto é configurado. O bloco dos dados iniciais (alínea 3.k da ficha 3) fica depois dessa linha e não é executado: é por isso que o comando funciona, apesar de a aplicação não arrancar.

Atenção. Correr o comando uma única vez. Se for corrido de novo, o Visual Studio responde que o nome BDInicial já é usado por uma migration. Se for preciso refazer a migration, a forma certa está na secção 3.

A ver, sem alterar: o ficheiro da migration

O ficheiro que o Visual Studio abriu é código C# gerado. Não é para alterar, mas vale a pena lê-lo: é a tradução direta das classes da ficha 3. Este é o excerto do método Up que cria a tabela Produtos:

<data>_BDInicial.cs (excerto do método Up, só para ler)

migrationBuilder.CreateTable(
    name: "Produtos",
    columns: table => new
    {
        Id = table.Column<int>(type: "int", nullable: false)
            .Annotation("SqlServer:Identity", "1, 1"),
        Nome = table.Column<string>(type: "nvarchar(100)", maxLength: 100, nullable: false),
        Detalhe = table.Column<string>(type: "nvarchar(200)", maxLength: 200, nullable: false),
        UrlImagem = table.Column<string>(type: "nvarchar(200)", maxLength: 200, nullable: true),
        Imagem = table.Column<byte[]>(type: "varbinary(max)", nullable: true),
        Preco = table.Column<decimal>(type: "decimal(10,2)", nullable: false),
        Promocao = table.Column<bool>(type: "bit", nullable: false),
        MaisVendido = table.Column<bool>(type: "bit", nullable: false),
        EmStock = table.Column<decimal>(type: "decimal(18,2)", nullable: false),
        Disponivel = table.Column<bool>(type: "bit", nullable: false),
        Origem = table.Column<string>(type: "nvarchar(max)", nullable: true),
        CategoriaId = table.Column<int>(type: "int", nullable: false),
        ModoEntregaId = table.Column<int>(type: "int", nullable: true)
    },
    constraints: table =>
    {
        table.PrimaryKey("PK_Produtos", x => x.Id);
        table.ForeignKey(
            name: "FK_Produtos_Categorias_CategoriaId",
            column: x => x.CategoriaId,
            principalTable: "Categorias",
            principalColumn: "Id",
            onDelete: ReferentialAction.Cascade);
        table.ForeignKey(
            name: "FK_Produtos_ModosEntrega_ModoEntregaId",
            column: x => x.ModoEntregaId,
            principalTable: "ModosEntrega",
            principalColumn: "Id");
    });
No ficheiro Vem de (classe Produto, ficha 3)
.Annotation("SqlServer:Identity", "1, 1") em Id A convenção: uma propriedade int Id é a chave primária, numerada pela base de dados a partir de 1
nvarchar(100) e nullable: false em Nome [StringLength(100)] e [Required]. O ? de string? não conta para a tabela: manda o [Required]
nvarchar(max) e nullable: true em Origem string? sem anotações: texto sem limite, que aceita nulos
decimal(10,2) em Preco e decimal(18,2) em EmStock [Column(TypeName = "decimal(10,2)")] num, o valor por omissão no outro
CategoriaId, nullable: false int CategoriaId: relação obrigatória
ModoEntregaId, nullable: true int? ModoEntregaId: relação opcional
onDelete: ReferentialAction.Cascade na chave de Categorias Como a relação é obrigatória, apagar uma categoria apaga os seus produtos
Nenhuma coluna categoria, modoentrega ou ImageFile As navegações não são colunas, e ImageFile tem [NotMapped]

Mais abaixo, no mesmo método, há duas instruções CreateIndex para CategoriaId e ModoEntregaId: o Entity Framework cria um índice em cada chave estrangeira, para as pesquisas por categoria e por modo de entrega serem rápidas. O método Down, no fim do ficheiro, faz o contrário de tudo isto: apaga as tabelas.

No projeto criado para SQL Server LocalDB (secção 0.6), o início do método Up não cria a tabela AspNetUsers, porque ela já está na migration do template. Em vez disso, acrescenta-lhe as colunas do ApplicationUser, uma a uma:

<data>_BDInicial.cs (excerto, só no projeto criado para SQL Server LocalDB)

migrationBuilder.AddColumn<string>(
    name: "Apelido",
    table: "AspNetUsers",
    type: "nvarchar(100)",
    maxLength: 100,
    nullable: true);

No projeto criado para SQLite, o mesmo ficheiro começa por um CreateTable para cada uma das tabelas do Identity, e a AspNetUsers já traz as colunas do ApplicationUser.

Verificar. Na pasta das migrations (secção 0.6) estão os ficheiros <data>_BDInicial.cs e <data>_BDInicial.Designer.cs, e o ApplicationDbContextModelSnapshot.cs. O método Up tem um CreateTable para Categorias, outro para ModosEntrega e outro para Produtos. Se o método Up estiver vazio, ou não tiver estas três tabelas, não avançar: ver a secção 3.

O que vamos fazer. Executar a migration: criar a base de dados FrutariaPWeb no LocalDB, com todas as tabelas.

Update-Database

A resposta, no projeto criado para SQL Server LocalDB:

Build started...
Build succeeded.
Applying migration '00000000000000_CreateIdentitySchema'.
Applying migration '20261028101532_BDInicial'.
Done.

No projeto criado para SQLite falta a linha da CreateIdentitySchema. A data na linha da BDInicial é a de cada um.

Porquê. O Update-Database usa a connection string do appsettings.json (a DefaultConnection da alínea 3.e da ficha 3) e faz o seguinte:

  1. liga-se ao servidor (localdb)\mssqllocaldb e, como a base de dados FrutariaPWeb não existe, cria-a;
  2. cria a tabela __EFMigrationsHistory, onde o Entity Framework regista as migrations já aplicadas;
  3. compara as migrations do projeto com as que estão registadas nessa tabela, e executa as que faltam, por ordem de data;
  4. regista cada migration aplicada na __EFMigrationsHistory.

Por isso, correr o comando outra vez não faz mal: responde No migrations were applied. The database is already up to date. e não altera nada.

Nota. A base de dados fica guardada em dois ficheiros, FrutariaPWeb.mdf (os dados) e FrutariaPWeb_log.ldf (o registo de transações), na pasta do utilizador do Windows (C:\Users\<utilizador>\). Não se mexe neles diretamente: quem os gere é o LocalDB.

Verificar. A consola termina com Done. e não mostra linhas a vermelho. Se aparecer um erro, ver a secção 4.3.

No projeto criado para SQL Server LocalDB, estas 12 colunas aparecem no fim da tabela, depois das do Identity, porque foram acrescentadas com AddColumn. No projeto criado para SQLite aparecem logo a seguir a Id. As duas formas estão certas.

__EFMigrationsHistory

Clique direito em dbo.__EFMigrationsHistory > Exibir Dados (View Data). A tabela tem duas colunas, MigrationId e ProductVersion (a versão do Entity Framework, 8.0.x), e uma linha por migration aplicada: duas no projeto criado para SQL Server LocalDB (00000000000000_CreateIdentitySchema e <data>_BDInicial), uma no projeto criado para SQLite.

Porquê. É esta a cadeia que a ficha descreve: do modelo de dados (MER) chegou-se às classes C# na ficha 3; das classes, com as migrations, chegou-se às tabelas. Cada tabela corresponde a uma classe registada no contexto, cada coluna a uma propriedade, e as chaves estrangeiras às relações. Por isso, para corrigir a base de dados, corrige-se a classe.

Nota. As tabelas AspNetUsers, AspNetRoles e AspNetUserRoles apareceram sem termos escrito classes para elas. Vêm do IdentityDbContext<ApplicationUser>, a classe base do nosso contexto, como a ficha explica na alínea d. As colunas que o ApplicationUser acrescenta entram na AspNetUsers, e não numa tabela à parte.

Verificar. As três tabelas da loja e a AspNetUsers têm as colunas das listas acima. Se faltar uma tabela ou uma coluna, ou se um tipo ou um nulo não bater certo, corrigir a classe na ficha 3 e refazer a migration (secção 3).

3. Quando a base de dados não sai certa

Se a alínea 3.d mostrar diferenças, o erro está nas classes da ficha 3, e não na base de dados. Corrige-se a classe e refaz-se a migration. A forma de a refazer depende de o Update-Database já ter sido executado.

3.1 Antes do Update-Database

A migration foi criada mas ainda não foi aplicada (por exemplo, a verificação do passo 3.a falhou):

Remove-Migration

Depois, corrigir as classes, compilar, e voltar a correr Add-Migration BDInicial.

Porquê. O Remove-Migration apaga a última migration e repõe a fotografia (ApplicationDbContextModelSnapshot.cs) como estava antes dela. Apagar os ficheiros à mão não chega: a fotografia ficava com o modelo errado, e a migration seguinte saía incompleta.

3.2 Depois do Update-Database

A migration já foi aplicada e a base de dados existe. Primeiro apaga-se a base de dados, depois a migration:

Drop-Database
Remove-Migration

O Drop-Database pede confirmação antes de apagar: responder que sim. Depois, corrigir as classes, compilar, e voltar a correr os dois comandos da ficha:

Add-Migration BDInicial
Update-Database

Porquê. O Remove-Migration recusa apagar uma migration que já está aplicada na base de dados (a mensagem diz has already been applied to the database). Depois de apagada a base de dados, a migration deixa de estar aplicada e já pode ser removida.

Atenção. No projeto criado para SQL Server LocalDB, o Remove-Migration só remove a última migration, a BDInicial. A 00000000000000_CreateIdentitySchema fica, e é assim que deve ser. Não a apagar.

Nota. Isto só se faz agora, enquanto a base de dados não tem dados que interessem. Mais tarde, para alterar uma base de dados com dados, cria-se uma migration nova (Add-Migration com outro nome) e aplica-se com Update-Database, sem apagar nada.

3.3 O que não fazer

  • Alterar tabelas ou colunas no designer do Visual Studio: a base de dados deixa de corresponder às classes e às migrations.
  • Editar os ficheiros da pasta das migrations à mão.
  • Apagar ficheiros de migrations no Gerenciador de Soluções em vez de usar Remove-Migration.
  • Acrescentar às classes as colunas das Figuras 6 e 7 que não estão neste guia (Titulo, DataNascimento, Localidade1, Localidade2).

4. Ponto de situação

4.1 Como fica o projeto

Nenhum ficheiro escrito por nós mudou. O que há de novo são os ficheiros da migration.

No projeto criado para SQL Server LocalDB:

GestaoLoja/                                       (pasta do projeto)
└── Data/
    └── Migrations/
        ├── 00000000000000_CreateIdentitySchema.cs           do template (ficha 3)
        ├── 00000000000000_CreateIdentitySchema.Designer.cs  do template (ficha 3)
        ├── <data>_BDInicial.cs                              NOVO (3.a)
        ├── <data>_BDInicial.Designer.cs                     NOVO (3.a)
        └── ApplicationDbContextModelSnapshot.cs             ALTERADO (3.a)

No projeto criado para SQLite:

GestaoLoja/                                       (pasta do projeto)
└── Migrations/                                   NOVA (3.a)
    ├── <data>_BDInicial.cs                       NOVO
    ├── <data>_BDInicial.Designer.cs              NOVO
    └── ApplicationDbContextModelSnapshot.cs      NOVO

Fora do projeto, no LocalDB: a base de dados FrutariaPWeb, com 11 tabelas, e os dados iniciais (três roles e o administrador), se a secção 2 tiver sido feita.

4.2 Lista de verificação

  1. O Update-Database terminou com Done., sem linhas a vermelho.
  2. A pasta das migrations tem <data>_BDInicial.cs, <data>_BDInicial.Designer.cs e ApplicationDbContextModelSnapshot.cs.
  3. No Pesquisador de Objetos do SQL Server, (localdb)\MSSQLLocalDB > Bancos de Dados tem FrutariaPWeb.
  4. FrutariaPWeb tem 11 tabelas: __EFMigrationsHistory, as sete AspNet..., Categorias, ModosEntrega e Produtos.
  5. Produtos tem 13 colunas, com CategoriaId sem nulos e ModoEntregaId com nulos, e não tem Titulo.
  6. ModosEntrega tem Nome sem nulos e Detalhe com nulos.
  7. AspNetUsers tem as 12 colunas do ApplicationUser, de Nome a DataRegisto.
  8. __EFMigrationsHistory tem a linha da BDInicial (e a da CreateIdentitySchema, no projeto criado para SQL Server LocalDB).
  9. A aplicação arranca com F5 (secção 2).
  10. AspNetRoles tem Admin, Gestor e Cliente, e AspNetUsers tem admin@localhost.com (secção 2).
